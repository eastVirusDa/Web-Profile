동시성 문제 해결 (Lost Update)

문제 정의

좋아요 기능에서 1,000명 동시 요청 시 데이터 정합성이 손상되는 문제가 발생했습니다. 기존 SELECT 후 UPDATE 방식은 조회와 갱신 사이에 Race Condition이 발생해, 여러 요청이 같은 값을 읽고 덮어쓰면서 좋아요 수가 유실됐습니다.

기술적 판단 및 해결

비관적 락(Pessimistic Lock)을 거는 대신 원자적(Atomic) UPDATE 쿼리로 변경해, DB 차원에서 읽기-수정-쓰기를 단일 연산으로 처리했습니다. 락으로 인한 처리량 저하 없이 정합성을 확보하는 쿼리 최적화 방식을 선택한 것이 핵심 판단이었습니다.

결과 및 성과

데이터 정합성 100%를 달성하면서 응답 시간도 2,610ms → 1,398ms로 46.4% 개선됐습니다. 락 경합을 피한 덕분에 정합성과 성능을 동시에 잡을 수 있었습니다.

N+1 문제 해결

문제 정의

주문 조회 시 연관 엔티티를 개별 조회하면서 N+1 문제로 DB에 32회 접근했고, 처리 시간이 122,861ms에 달하는 심각한 성능 저하가 있었습니다.

기술적 판단 및 해결

배치 쿼리를 적용하고 JOIN을 통한 단일 쿼리 통합으로 연관 데이터를 한 번에 조회하도록 개선했습니다. 반복 조회를 묶어 DB 왕복 횟수 자체를 줄이는 데 집중했습니다.

결과 및 성과

DB 접근이 32회 → 5회로 84% 감소했고, 처리 시간은 122,861ms → 74,627ms로 39.3% 단축됐습니다.

무한 스크롤 — 커서 기반 페이지네이션

문제 정의

기존 OFFSET 기반 페이지네이션은 뒤쪽 페이지로 갈수록 건너뛰는 행이 많아져 성능이 선형적으로 저하됐습니다. 60,000건 이상의 상품 데이터 환경에서 깊은 페이지 조회가 특히 느렸습니다.

기술적 판단 및 해결

마지막으로 조회한 레코드의 키를 기준으로 다음 페이지를 가져오는 커서(Cursor) 기반 페이지네이션으로 전환해, 페이지 깊이와 무관하게 일정한 조회 비용을 유지하도록 설계했습니다.

결과 및 성과

100페이지: 500ms → 12ms (약 40배 개선), 500페이지: 2,000ms → 12ms (약 166배 개선)을 달성했고, 데이터베이스 부하를 99% 감소시켰습니다.

프로젝트 소개

노년층을 위한 RAG(Retrieval-Augmented Generation) 기반 멀티 카테고리 상담 챗봇 시스템입니다. 일자리 · 복지 · 법률 · 뉴스 · 금융사기 등 서로 다른 5개 영역의 행정 정보를, 노년층이 이해하기 쉬운 형태로 안내하는 것을 목표로 했습니다. LangGraph 기반 멀티 에이전트 구조와 다단계 검색 전략으로 답변 제공률과 응답 속도를 함께 끌어올렸습니다.

LangGraph 기반 멀티 에이전트 워크플로우 설계

문제 정의

5개의 서로 다른 카테고리(일자리 · 복지 · 법률 · 뉴스 · 금융사기)가 각각 다른 데이터 소스, 검색 전략, 프롬프트를 필요로 했습니다. 단순 if-else 분기로는 코드 복잡도가 기하급수적으로 증가했고, 카테고리를 추가할 때마다 기존 코드 전체를 수정해야 해 유지보수 비용이 컸습니다.

기술적 판단 및 해결

CategoryHooks 추상 클래스를 설계해 카테고리별 동작을 인터페이스화하고, 팩토리 패턴으로 모든 노드(rewrite · retrieve · grade · generate 등)를 함수형으로 생성했습니다. 또한 런타임 레지스트리로 서버 시작 시 모든 그래프를 미리 컴파일·캐싱해, 카테고리 확장 시 공통 워크플로우를 재사용할 수 있는 구조를 만들었습니다.

결과 및 성과

새로운 카테고리를 추가할 때 기존 코드를 수정하지 않고 훅과 설정만으로 확장할 수 있게 되어, 카테고리 확장성과 공통 워크플로우 재사용성을 동시에 확보했습니다.

다단계 검색 전략 (Multi-Level Search Strategy)

문제 정의

첫 벡터 검색에서 관련 문서를 찾지 못하는 경우가 빈번했고, 그때 사용자에게 "정보 없음"으로 응답하면 서비스 신뢰도가 하락했습니다. 특히 노년층 대상 서비스에서는 답변 제공률이 무엇보다 중요했습니다.

기술적 판단 및 해결

검색이 실패했을 때 단계적으로 범위를 넓히는 3단계 폴백 전략을 구현했습니다.

① Filter Widening — 지역/연령 필터를 단계적으로 확장 (최대 2회)
② Query Rewriting — LLM으로 쿼리를 재작성한 뒤 재검색 (최대 1회)
③ Web Search — SerpAPI를 통한 실시간 웹 검색 (최대 1회)

결과 및 성과

3단계 폴백 검색 전략(필터 확장 → 쿼리 재작성 → 웹 검색) 구현으로 쿼리 성공률 85%+를 달성하고, 1~2초 내 응답 시간을 확보했습니다.

FastAPI 기반 RESTful API 서버 구축

문제 정의

프론트엔드와 백엔드 간 API 인터페이스 정의가 필요했고, 개발/운영 환경별로 CORS 설정이 달라야 했으며, LLM 호출에 대한 디버깅과 모니터링이 어려웠습니다.

기술적 판단 및 해결

단일 엔드포인트(/agent/query)로 모든 카테고리를 처리하되 카테고리 필드로 내부 분기하도록 설계해 인터페이스를 단순화했습니다. 환경별 CORS 미들웨어(개발: localhost:3000 / 운영: 실제 도메인)를 구성하고, LangSmith 추적을 선택적으로 활성화해 LLM 호출 흐름을 관측 가능하게 만들었습니다.

결과 및 성과

프론트엔드가 단일 계약으로 모든 카테고리를 호출할 수 있게 됐고, 환경 분리와 추적 체계를 통해 안정적인 개발·운영과 LLM 호출 디버깅이 가능해졌습니다.
